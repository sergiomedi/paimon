## Why this one is kept

Every other file in this directory was written by a person running `measure.sh` against
an environment they had provisioned themselves. This one was written by nobody. A push to
`main` created the environment, built the image, deployed it, migrated the schema, obtained
a token, ingested a document, asked a question about it, recorded these numbers and
destroyed everything — in 27 minutes and 46 seconds, on the tenth attempt.

It is kept as the reference for that, and later runs are not. Their numbers live in the
run's artifact and no further: a directory with one measurement per merge stops being a set
of findings and becomes a log, and the value of this directory is that everything in it is
something that cannot be obtained again.

The zero above is the honest part. The telemetry did not arrive inside the environment's
lifetime, and this run cannot say whether that is an exporter that failed or a question
asked 60 seconds after the requests, when Application Insights ingestion takes between one
and five minutes. `measure.sh` now polls instead of sleeping once, and records how long it
waited — so the next run of this answers a question that this one could only raise.

> **Answered, by run 12.** The traces do arrive: the first was readable **30 seconds** after
> the request that produced it. So the zero here was not a broken exporter but variance in
> ingestion, and a single question asked at 60 seconds that happened to fall the wrong side
> of it. Asking earlier got a better answer than asking later, which is the shape of
> variance rather than of latency — and the reason this file is left as it was written.
> Deleting a wrong-looking number after it turns out to have an explanation is how a
> measurements directory stops being evidence.
